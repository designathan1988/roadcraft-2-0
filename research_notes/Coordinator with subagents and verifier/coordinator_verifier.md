# Coordinator conversation, worker subagents, independent verifier

Research for: can the main conversation coordinate, delegate the work to subagents and verify it, without the run taking hours?
All pages below were fetched on 2026-10-24. Quotes are kept short; the rest is paraphrase.

## Sources fetched

| Source | What it says that matters here |
|---|---|
| [Subagents](https://code.claude.com/docs/en/sub-agents) | `--agent <name>` (or `agent` in `.claude/settings.json`) runs the main thread with that agent's tools and model. `Agent(worker, verifier)` in `tools` is an allowlist of the types the main thread may spawn. Per-agent `tools`, `disallowedTools`, `model`, `effort`, `maxTurns`, `isolation: worktree`, `hooks`. Subagents spawned from the main conversation start in the background; up to 20 run at once. A subagent sees only its delegation message, not the conversation. A per-invocation `model` overrides the definition. |
| [Agent teams](https://code.claude.com/docs/en/agent-teams) | Experimental, off by default. Lead + teammates + shared task list; a `TaskCompleted` hook that exits 2 refuses the completion and sends feedback. Advice: 3-5 teammates, 5-6 tasks each, each teammate owns different files, the lead sometimes starts implementing itself instead of waiting. Much higher token use than subagents. |
| [Dynamic workflows](https://code.claude.com/docs/en/workflows) | A JS script (`agent()`, `parallel()`, `pipeline()`, `schema` for JSON results) runs subagents in the background; results stay in script variables, so the conversation keeps only the final answer. Up to 16 concurrent agents by default, 1,000 per run. No mid-run user input: one stage per workflow when sign-off is needed. Can be saved as `/name` in `.claude/workflows/`. Documented pattern: "adversarially verify each finding before reporting it". Desktop shows an approval card. |
| [/goal](https://code.claude.com/docs/en/goal) | A prompt-based Stop hook: a small fast model judges the condition from the transcript only; "It doesn't run commands or read files independently". So it cannot check images or numbers the worker did not surface. |
| [Hooks reference](https://code.claude.com/docs/en/hooks) | SubagentStop receives `agent_type`, `agent_transcript_path`, `last_assistant_message`; `decision: "block"` keeps the subagent working with `reason` as its next instruction; matcher filters by agent type. Agent-type hooks can use Read, Grep, Glob; experimental; 60 s default timeout. |
| [Worktrees](https://code.claude.com/docs/en/worktrees) | Subagent worktrees branch from the default branch unless `worktree.baseRef` is `"head"`. A worktree is a fresh checkout: dependencies must be installed there. |
| [Best practices](https://code.claude.com/docs/en/best-practices) | Four ways to gate the stop: prompt, `/goal`, Stop hook, verification subagent in fresh context. Show evidence, not assertions. The reviewer "sees only the diff and the criteria you give it". Tell it to flag only gaps that affect correctness or the stated requirements, or it pushes towards over-engineering. |
| [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) | Orchestrator-worker. Parallel subagents cut research time by up to 90 %. Multi-agent runs use about 15x the tokens of chat. Each subagent needs an objective, an output format, tool guidance and task boundaries. Judge: one LLM call with a rubric, scores and pass/fail. |
| [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | Orchestrator-workers when subtasks are not known in advance; evaluator-optimizer when there are clear evaluation criteria. Agents need ground truth from the environment (tool results, code execution) at each step. |
| [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps) | Generator and evaluator kept apart because self-evaluation is too generous; a standalone evaluator tuned to be skeptical is more tractable. Evaluator drove the live page with Playwright, had a hard threshold per criterion, and a "sprint contract" fixed what done meant before each chunk. Files carried the hand-offs. Cost: solo 20 min / $9 against harness 6 h / $200. |

## What this means for roadcraft

1. **Separate the three roles physically, not by text.** Coordinator: the main thread started with `--agent coordinator`, with no Edit/Write and `Agent(worker, verifier)`. Worker: edits, runs, commits. Verifier: fresh context, `disallowedTools: Edit, Write, NotebookEdit, Agent`, receives only the contract and the commit, re-runs the measurements itself.
2. **Contract before the work** (the "sprint contract"): per stage, a JSON file with measurable criteria and the command that proves each one: triangles by `scripts/model-catalog.mjs` / `scripts/optimization-sheet.mjs`, `npm run verify` (and `--game` for the picture, compared by `scripts/look-compare.mjs`), no change under the protected rulers (`git diff --stat base..commit -- tests scripts/baselines ...`), feature list unchanged.
3. **Verdict per criterion with a hard threshold**, as JSON. One failed criterion fails the stage. The verifier opens every before/after image itself.
4. **Bounded loop for speed**: worker -> verifier -> on failure, the same worker is resumed with only the failed criteria -> verifier again; at most 2 retries, then "not done" with evidence to the user. Independent stages run in parallel (3-5), in the background.
5. **Cost is real**: parallel agents save wall-clock time but multiply tokens (15x chat in the research system; 20x for the long harness).
6. **Unverified here**: whether `agent` in settings / `--agent` applies to sessions started from the Desktop app; whether worktree subagents are practical with this repo's `node_modules` (each worktree needs its own install or a link).
